# EcaSystems — согласованные изменения для следующей итерации

## Контекст

Работаем от актуального локального кода ветки `cancellation`.

Эта инструкция **заменяет предыдущие инструкции по cancellation**. Если старые `.md`-файлы в репозитории противоречат этому документу, приоритет у этого документа.

Перед изменениями обязательно изучить актуальные локальные файлы проекта, особенно:

```text
Runtime/Core/Base/
Runtime/Core/Execution/
Runtime/Unity/EcaSystemsSmokeTest.cs
```

Главная цель этой итерации — **максимально упростить Execution layer**.

Мы отказываемся от cancellation/reset/queue-механики на текущем этапе. Execution нужен только для учёта конкретных запусков Rule во времени, overlap `Allow/Ignore` и ограничения общего количества фактических запусков.

# 1. Что остаётся задачей Execution layer

Execution layer отвечает только за:

```text
Rule
↓
конкретные Execution этого Rule
↓
их lifecycle
↓
поведение при повторном Fire
↓
ограничение количества фактических запусков
```

В текущей версии нужны:

```text
Overlap:
- Allow
- Ignore

Limit:
- -1 = unlimited
- 0 = ни одного запуска
- N > 0 = максимум N фактических запусков
```

Не реализовывать сейчас:

```text
Cancel
Reset
Queue
Pause
Resume
Save/Load execution state
Command history
Interruptible Action
Execution history/debugging
```

# 5. Lifecycle выполнения перенести обратно в Group

`EcaRuleExecutionGroup<TEventContext>` сама:

1. создаёт `EcaRuleExecution<TEventContext>`;
2. добавляет её в `_executions`;
3. переводит в `Running`;
4. вызывает `_ruleRunner.Run(execution.Rule, execution.Context)`;
5. после успешного завершения ставит `Completed`;
6. при exception ставит `Failed` и сохраняет exception;
7. увеличивает `EcaRuleExecutionTotalFinished`;
8. удаляет execution из active `_executions`.

Концептуально:

```csharp
private async Task Execute(EcaRuleExecution<TEventContext> execution)
{
    try
    {
        execution.MarkRunning();

        var task = _ruleRunner.Run(execution.Rule, execution.Context);
        if (task == null)
            throw new InvalidOperationException("Rule runner returned null Task.");

        await task;

        execution.MarkCompleted();
    }
    catch (Exception exception)
    {
        execution.MarkFailed(exception);
    }
    finally
    {
        State.IncrementFinished();
        _executions.Remove(execution);
    }
}
```

Не нужно копировать этот snippet буквально, если актуальный локальный код требует небольших адаптаций.

Важно сохранить semantics:

```text
MarkRunning
→ IncrementStarted через текущую модель
→ Run
→ Completed / Failed
→ IncrementFinished
→ remove active execution
```

Обычный `OperationCanceledException`, если пользовательская Action сама его бросит, в EcaSystems сейчас не имеет специальной cancellation semantics и может обрабатываться как обычный failure.

# 6. Новый `EcaRunMode`

Вместо передачи отдельных `overlap`, `once`, `DoN`, `limit` и т.п. использовать **один объект конфигурации**:

```text
RunMode
├── Overlap
└── Limit
```

Добавить:

```text
Runtime/Core/Execution/EcaRunMode.cs
```

Рекомендуемая форма:

```csharp
public sealed class EcaRunMode
{
    public EcaOverlap Overlap { get; }
    public int Limit { get; }

    public EcaRunMode(EcaOverlap overlap, int limit = -1)
    {
        if (limit < -1)
            throw new ArgumentOutOfRangeException(nameof(limit));

        Overlap = overlap;
        Limit = limit;
    }
}
```

Разрешённые значения `Limit`:

```text
-1  = unlimited
0   = Rule никогда не создаёт Execution
1   = максимум один фактический запуск
N   = максимум N фактических запусков
```

Любой:

```text
-2
-3
...
```

считать ошибкой конфигурации и бросать `ArgumentOutOfRangeException`.

Не создавать отдельные abstractions:

```text
EcaExecutionLimit
Once
DoN
Times(...)
```

Они не нужны.

# 9. Semantics `Limit`

Проверка limit находится в Group.

Проверять **до создания новой Execution**.

Концептуально:

```csharp
if (RunMode.Limit >= 0 &&
    State.EcaRuleExecutionTotalStarted >= RunMode.Limit)
{
    return;
}
```

После этого применять overlap:

```csharp
switch (RunMode.Overlap)
{
    case EcaOverlap.Ignore:
        if (_executions.Count > 0)
            return;
        break;

    case EcaOverlap.Allow:
        break;

    default:
        throw new NotSupportedException(...);
}
```

И только затем создавать Execution.

## Важная semantics

`Limit` считает **фактически начавшиеся executions**, а не количество Event Fire.

Пример:

```text
RunMode:
Overlap = Ignore
Limit = 2

Fire #1 → Execution #1 стартует
Started = 1

Fire #2 пока #1 Running
→ Ignore
Started всё ещё = 1

#1 завершилась

Fire #3
→ Execution #2 стартует
Started = 2

Fire #4
→ limit reached
→ ничего не запускается
```

Игнорированный Fire не расходует limit.

Condition при этом уже могла быть проверена Engine, потому что сохраняется текущая фундаментальная semantics:

```text
все Conditions одного Fire
проверяются раньше любых Actions этого Fire
```

Limit/Overlap применяются после Conditions внутри Group.

# 10. `Once` и `DoN` не являются отдельными режимами

Не добавлять в код:

```text
Once
DoN
```

Их semantics теперь выражается только через `Limit`.

```text
Limit = 1
→ once

Limit = 3
→ максимум три запуска
```

Вопрос:

```text
один раз за игру?
один раз за сцену?
один раз для NPC?
```

не решается Execution layer.

Позже это определяется lifetime конкретной `ExecutionGroup` через Scope layer.

Пример будущей semantics:

```text
Global Scope + Limit 1
→ один раз за lifetime Global Scope

Scene Scope + Limit 1
→ один раз за lifetime Scene Scope

NPC/local Scope + Limit 1
→ один раз для конкретного local scope
```

Scope в этой итерации **не реализовывать**.

# 11. Изменить `EcaExecutionEngine`

Удалить dependency:

```text
IEcaExecutionExecutor
```

Добавить/использовать:

```text
IEcaRuleRunner
```

Концептуально Engine держит:

```csharp
private readonly IEcaRuleRunner _ruleRunner;
```

Default composition создаёт обычный:

```csharp
new EcaRuleRunner()
```

`Register` теперь принимает `EcaRunMode`.

Концептуально:

```csharp
public void Register<TEventContext>(
    IEcaRule<EcaExecutionContext<TEventContext>> rule,
    EcaRunMode runMode);
```

При registration передавать `runMode` и shared `IEcaRuleRunner` в `EcaRuleExecutionRegistry`.

Сохранить текущий rollback:

```text
RuleRegistry.Register
↓
ExecutionRegistry.Register

если второй шаг упал
↓
RuleRegistry.Unregister
↓
rethrow
```

Не менять фундаментальный `Fire` pipeline:

```text
1. Selector получает Rules
2. для каждого Rule создаётся EcaExecutionContext
3. Checker проверяет ВСЕ Conditions
4. собираются прошедшие Group + Context
5. только после этого Group.Fire для прошедших Rules
```

# 12. Изменить `IEcaRuleExecutionRegistry` / `EcaRuleExecutionRegistry`

`Register` больше не принимает:

```text
EcaOverlap
IEcaExecutionExecutor
```

Новый conceptual API:

```csharp
void Register<TEventContext>(
    IEcaRule<EcaExecutionContext<TEventContext>> rule,
    EcaRunMode runMode,
    IEcaRuleRunner ruleRunner);
```

Registry создаёт:

```csharp
new EcaRuleExecutionGroup<TEventContext>(
    rule,
    runMode,
    ruleRunner);
```

При повторной регистрации существующей Group сохранить текущую validation:

- group должна принадлежать тому же Rule;
- generic context type должен совпадать;
- конфигурация RunMode должна совпадать.

Для сравнения RunMode не нужно вводить отдельную equality-архитектуру. Достаточно сравнить:

```text
existing.RunMode.Overlap
existing.RunMode.Limit
```

Если mode отличается — `InvalidOperationException`.

Registry остаётся storage по:

```text
RuleId → IEcaRuleExecutionGroup
```

Не менять key model.

# 16. Queue и Reset полностью отложить

Не реализовывать Queue.

Не реализовывать Reset.

Не оставлять новый production-код, предназначенный только для них.

Причина:

- Queue сейчас не нужен для первого простого Execution;
- Reset требует настоящего механизма interruptible/resumable Action;
- обычный `Task` framework не может универсально прервать в произвольной точке.

Будущий advanced execution может потребовать явной последовательности Commands/steps и history/program-counter model для:

```text
interrupt
resume
save/load
pause
reset
```

Но это не часть этой итерации.

## Добавить тесты `RunMode / Limit`

Обязательно проверить:

### Unlimited

```text
new EcaRunMode(EcaOverlap.Allow)
```

несколько последовательных запусков разрешены.

### Limit = 1

```text
new EcaRunMode(EcaOverlap.Allow, 1)
```

после одного фактического запуска новые executions не создаются.

### Limit = N

Например:

```text
new EcaRunMode(EcaOverlap.Allow, 2)
```

запускаются максимум две executions.

### Ignore не расходует limit

```text
Overlap = Ignore
Limit = 2
```

Fire во время active execution игнорируется и не увеличивает `TotalStarted`.

### Limit = 0

Rule не создаёт executions.

### Invalid limit

```text
new EcaRunMode(EcaOverlap.Allow, -2)
```

бросает `ArgumentOutOfRangeException`.

Не привязываться к старому числу PASS. После удаления cancellation tests количество assertions закономерно изменится.

В финальном отчёте показать новое:

```text
PASS X, FAIL 0
```

# 20. Итоговая mental model после изменений

```text
EcaExecutionEngine
│
├── RuleRegistry / Selector / Checker
├── ExecutionRegistry
├── ContextFactory
└── RuleRunner
        │
        ▼
EcaRuleExecutionGroup<TEventContext>
│
├── Rule
├── RunMode
│   ├── Overlap: Ignore | Allow
│   └── Limit: -1 | 0 | N
├── GroupState
│   ├── TotalStarted
│   └── TotalFinished
└── active Executions
        │
        ▼
EcaRuleExecution<TEventContext>
├── Rule
├── Context
├── Status
└── Exception
```

Execution layer отвечает только на два дополнительных вопроса поверх Base ECA:

```text
1. Есть ли уже выполняющиеся запуски этого Rule и можно ли создать ещё один?
2. Не исчерпан ли общий лимит фактических запусков этой ExecutionGroup?
```
